## 一、为什么 13 册 §4.2 是和稀泥

13 册当时给的分工是：

> 首页是「收件箱」（保留紧凑任务列表 + 强化失败区），任务页是「账本」，抽屉是「档案」。

这个方案我现在自己判它不成立，理由一条：

> **如果一份数据在两个页面都必须出现，那这两个页面就应该是一个页面。**

「收件箱」和「账本」的区别只有**筛选条件**和**排序**——`failed` 优先 vs 按时间倒序。而任务页的 `filter-strip` 里**已经有一个「失败」筛选**（`TasksPage.tsx:31`）。

也就是说 13 册 §4.2 的方案，本质是：

```
首页  = 任务页 + 预置筛选(failed) + 换一套视觉语言重画一遍
```

这不是分工，是**给同一个列表做了两套皮肤**。用户的原话说得比我准：

> 「我觉得是有点重复啊 都在展示任务列表 难道不是吗」

是。而且 §0 的证据说明，首页那套皮肤连独有信息都没有。

### 什么情况下首页才应该存在

首页存在的正当理由只有一个：**它要回答任务列表回答不了的问题**。比如：

- 跨任务的趋势（本周修复率、平均耗时、失败码分布）
- 系统级的健康与容量（并发水位、轮询延迟、磁盘）
- 需要决策的汇总（「3 个项目未体检，是否批量运行」）

**当前首页一个都没有。** 它的 `metrics` 三个数字（处理中 / 已完成 / 需要处理）是对下方列表的**计数**，不是列表之外的信息。

> 等以后真有了趋势与容量视图，再开一个「概览」页——**那时它有独占信息，不再是重复。** 现在没有。

### 2.2 关键决定逐条

**① 不做「需要处理」独立分区块 —— 只做排序置顶 + 一条分隔标注**

我和 GPT 在这里有分歧。GPT 倾向完全打平（只靠筛选），我不同意，但也不做独立卡片区。

理由：

- **完全打平不行**：`failed` 和 `awaiting_start` 是**待办**，其余是**进度**。8 条任务里有 3 条待办时，如果按 `updated_at` 排序，它们会散落在 33 条已完成中间。「有没有事要我做」这个问题需要扫完全表才能回答
- **独立卡片区也不行**：那就又变成"同一条任务出现两次"或"两套视觉语言"，回到首页的老问题

所以：**同一张表、同一套行样式、同一份数据，只改排序，加一条 `<div class="ledger-divider">` 标注分界。** 筛选到「失败」时置顶区自然消失（因为全表都是它）。

置顶规则（写死，不做配置）：

```
1. failed
2. awaiting_start
3. 其余按 updated_at 倒序
```

**② 第三列改为「进展 / 结果」互斥列 —— 不加列**

现状 `.task-table` 是 `112px minmax(280px,1fr) 110px 30px` 四列，第三列 `resultLabel()` 在任务跑完前恒为 `—`。**处理中的任务，这一列永远是个破折号。**

改为按状态互斥：

| 任务状态 | 第三列显示 |
|---|---|
| `running` / `queued` / `cancel_requested` | 相对时间「2 分前」（`updated_at` 差值） |
| `failed` | 失败码对应的短标题（`failureTitle[code]`，取现成的） |
| `completed` | 「已修复」/「无需修改」 |
| `awaiting_start` | 空 |

**为什么不显示「当前阶段名」**：§0 已经证明列表接口不返回 `stages`。要显示阶段名必须改后端 SQL。**这一轮不碰后端**，用 `updated_at` 相对时间代替——它同样回答「这任务活着吗、卡住了吗」，且零后端改动。

> 如果后续愿意改后端，在 `list_tasks()` 里 JOIN 一个 `current_stage_id` 是最小改动，届时这一列换成「修复 · 2 分」即可，列宽不用动。

**③ 顶部不加控制栏 —— 已有的够了**

GPT 和用户都提到「状态那些小东西缩小放上面」。我的判断是**连缩小都不必，因为它们已经在别处了**：

| 信息 | 现在在哪 | 结论 |
|---|---|---|
| 执行模式（全自动 / 待我开始） | `topbar` 中央的 `ModeController`，全局常驻 | 已有，别重复 |
| 环境健康 | `navrail` 底部 `.nav-health` 心跳点，全局常驻 | 已有，别重复 |
| AI 并发 3/4 | 设置页 | **属于设置**。日常看任务时它是噪音 |
| 轮询频率 | 无 | 不必要（见 §3 口径问题） |

页面标题下**只加一行计数摘要**：

```
8 条 · 2 处理中 · 3 需要处理
```

这一行替代了原首页的三个大数字 metrics。**同样的信息，从 88px 高的三栏格子压缩到一行 13px 文字。** 这就是"缩小信息"的正解——不是搬到别处，是降权。

**④ 删掉 `TASK LEDGER` kicker**

页面已经是唯一入口，`<h1>任务</h1>` 上面不需要英文标签。这是 14 册 A1 在本页的落实。

**⑤ 列表本身不缩**

用户说「不知道任务列表要不要缩，因为我都没见过」。我的判断：**账本行现在已经很克制**（状态 / 工单号+标题 / 结果 / 箭头，70px 行高），本轮改造做得好的地方就是它。**不缩。** 真要减，减的是行高的 `min-height: 70px` → 62px，但那要等看到 30+ 条真实数据后再定，现在动是瞎猜。

## 七、施工后在真机上发现的第二处「信息在骗人」

施工完成后到 `http://10.101.0.8:9522/` 实截，真机是**空库**——零任务、零来源、零项目。这一屏此前从未被任何截图覆盖过（第一轮 41 张和第二轮 41 张都是 mock 满态），但它恰恰是**新用户打开系统的第一屏**。而任务页升为落地页之后，它的分量比以前重了一个量级。

三处问题当场暴露，其中两处是我自己这一轮引入的：

### 7.1 全 0 的计数行（我引入的）

```
任务
0 条 · 0 处理中 · 0 需要处理     ← 三个 0 说的是同一件事
[全部][处理中][待开始][失败][已完成]  ← 筛选 0 条任务
        ┌────────────────────────┐
        │   暂无符合条件的任务      │  ← 第三次说
        └────────────────────────┘
```

计数摘要是用来替代原首页三栏 metrics 的，前提是**有账可计**。零任务时它和筛选条一起，变成了空态卡片的两次前置复读——正是本轮要消灭的那类重复，只是换了个地方长出来。

**改法**：`counts.total===0` 时，计数行、筛选条、「刷新账本」按钮全部不渲染。空账本不需要筛选器，也不需要一个刷不出东西的按钮。

### 7.2 空态只说「这里没有」，不说「那该做什么」

原文案「暂无符合条件的任务 / 界面更新于 刚刚 · 新问题进入后会出现在这本任务账里」——在**有来源、只是暂时没工单**时是准确的；在**一个来源都没接**时是误导：新问题永远不会进入，因为没有任何通路。

**改法**：空账本时补查 `/api/providers` 与 `/api/projects`（仅在 `items.length===0` 时查，有任务就不查，不增加常态请求），分两种形态：

| 条件 | 标题 | 形态 |
|---|---|---|
| 有来源且有项目 | 这本任务账还是空的 | 原样，绿色呼吸心跳 = 在等 |
| 缺来源或缺项目 | 还没有可以收问题的通路 | 两步引导 + 灰色静止心跳 = 不通 |

两步引导用的是账本自己的语言——1px 描边分隔的两行，`01/02` 等宽序号，完成的变 `✓` 且转灰，未完成的右侧带「去配置」直接跳页。**不是**新造一个 onboarding 组件，是把同一套行式排版复用到空态里。

### 7.3 「轮询与依赖正常」在零来源时是错的（既有问题）

左下角 `nav-health` 在 `readiness==='ready'` 时写「轮询与依赖正常」。实测 `/api/readiness` 的 10 个检查项：

```
config.loaded / storage.data_root / sqlite.wal / frontend.dist
dependency.{git,svn,claude-code,codex,opencode,gh}-cli
```

**全部是平台自检，没有一项关心有没有接来源。** 依赖确实正常，但"轮询"无从谈起——零 provider 时没有任何东西在被轮询。于是出现了「主区说没有通路 / 侧栏说轮询正常」的自相矛盾。

**改法**：文案改为「依赖与运行环境正常」。只删掉一个无依据的词，不动后端、不加检查项。

> 这三条都不是"审美"问题，是**界面在陈述一件与事实不符的事**。视觉评审能抓到它们，是因为第一屏的信息层级本身就是视觉设计的一部分——一个 0 摆在 h1 下面，和一个 0 藏在折叠区里，重量完全不同。

### 7.4 连带的测试补充

新增 `@visual first-run ledger asks for a source instead of claiming standby`，覆盖零任务 + 零来源 + 零项目分支，断言：引导标题存在、`.ledger-summary` / `.filter-strip` / 「刷新账本」三者 `toHaveCount(0)`、点「去配置」真的落到来源页。新增基线 `tasks-first-run-light.png`。

至此 e2e 4 条全绿，`tsc --noEmit` / `npm run build` / `vitest run` 全通过。
